# cgbg-project 모노레포 전환 및 MVP 개발 계획

상태: 1단계 모노레포 구조 전환 완료. 온보딩·면접 앱을 독립 실행하며 기존 Supabase 코드를 shared 패키지로 이동했다. 개발 서버, 타입·lint 검사, 유닛 5개와 프로덕션 E2E 2개를 확인했다. 제품 기능, DB 변경과 클라우드 배포는 아직 수행하지 않았다.

이해한 범위: 아이디어를 문서화하고, 현재 단일 Next.js 보일러플레이트를 구직자 온보딩 앱과 에이전트 면접 앱으로 나누는 실행 계획을 제안한다.

제품 요구사항의 기준은 [제품 아이디어](../01_product_idea.md), 코드·테스트 제한의 기준은 [프로젝트 개요](../00_overview.md#코드-및-테스트-제한)다.

## 확정 사항과 제안 사항

- 확정: Next.js·Vercel·Supabase 스택과 npm 유지, 독립된 Next.js 앱 2개.
- 확정: 실제 Claude 대화와 샘플 기업·채용공고, 가상 구직자 1명, 로그인 없이 시연.
- 제안: npm workspaces와 공유 패키지 1개로 구성한다. Turborepo와 별도 백엔드 앱은 초기에는 추가하지 않는다.
- 제안: 첫 데모는 샘플 공고 3개, 기업별 대화는 정해진 최대 턴 안에서 종료한다. 정확한 턴·동시 실행·비용 한도는 면접 엔진 구현 전에 확정한다.
- 제안: 실제 자료 업로드·외부 연동·캘린더 예약은 후속 범위로 둔다.

## 목표 구조

아래는 생성 예정 구조이며 현재 존재하는 파일 목록이 아니다.

```text
cgbg-project/
  apps/
    onboarding/                 # @cgbg/onboarding, 개발 포트 3000
      src/app/                  # 가상 자료 확인, 구직자 인터뷰, 프로필 확인
      next.config.ts
      tsconfig.json
      vitest.config.mts
      package.json
      .env.example
    interviews/                 # @cgbg/interviews, 개발 포트 3001
      src/app/                  # 진행 목록, 대화 상세, 결과와 확인 질문
      src/app/api/              # 면접 실행·진행 조회 서버 처리
      next.config.ts
      tsconfig.json
      vitest.config.mts
      package.json
      .env.example
  packages/
    shared/                     # @cgbg/shared
      src/supabase/             # 기존 클라이언트·환경변수 검증·테스트 이동
      src/types.ts              # 두 앱이 실제로 사용하는 데이터 계약
      package.json
      tsconfig.json
      vitest.config.mts
  tests/e2e/                    # 두 앱 사이 흐름 검증
  docs/
    onboarding/00_overview.md   # 구현 시 앱별 책임·실행 정보 작성
    interviews/00_overview.md
    00_overview.md
    01_product_idea.md
    plan/
    etc/

  package-lock.json             # 루트 lockfile 1개
  eslint.config.mjs
  vitest.config.mts             # workspace별 Vitest 설정 수집
  playwright.config.ts
  AGENTS.md
  README.md
```

앱별 디자인 시스템이나 공용 UI 패키지는 먼저 만들지 않는다. 실제 중복이 생기면 필요한 부분만 공유한다.

## 앱과 데이터의 책임

| 영역 | 책임 |
| --- | --- |
| onboarding | 가상 이력서 확인, Claude의 구직자 인터뷰, 희망 조건 수정, 확정 프로필 저장 |
| interviews | 샘플 공고 선택, 구직자·채용 에이전트 대화 실행, 진행 상태·근거·결과 표시, 확인 질문 응답 |
| shared | 기존 Supabase 클라이언트와 두 앱이 함께 사용하는 프로필·공고·대화·상태 타입 |
| Supabase | 앱 간 프로필과 실행 결과 공유; 실제 스키마와 접근 정책은 기능 구현 시 작성 |

두 앱이 서로의 `src/`를 직접 import하지 않는다. 공유 코드는 workspace 패키지의 명시적인 export로 사용한다. Supabase 브라우저·서버 진입점을 분리하고, 서버 전용 코드가 브라우저 번들에 섞이지 않게 한다.

온보딩 완료 후 면접 앱의 URL로 이동한다. 프로필 전문이나 비밀정보를 URL에 넣지 않는다. 공유할 실행 식별자와 데이터는 서버에서 확인하며, 실행별 상태를 분리해 서로 다른 시연이 결과를 덮어쓰지 않게 한다. 로그인 없는 가상 데이터 데모를 실제 개인정보에 대한 접근 제어로 재사용하지 않는다.

Claude 호출은 각 앱의 서버 코드에서만 수행한다. 구직자 인터뷰는 onboarding, 기업별 면접은 interviews가 담당한다. 프론트엔드와 독립적인 서버 실행이 요구사항으로 확정되었으므로, 실행 기반은 [최신 온보딩·면접 계획](20261024_1132_onboarding_agents_plan.md)의 지속 작업 방식으로 설계한다.

## 1단계: 실행 가능한 두 앱으로 분리

이 단계는 제품 기능 구현과 분리한다. 먼저 두 앱의 기본 화면, 공유 import, 검사 명령이 동작하는지 확인한다.

| 현재 위치 | 변경 대상과 주의점 |
| --- | --- |
| `src/app/` | `apps/onboarding/src/app/`로 이동; interviews에는 최소 layout·page·스타일 생성 |
| `src/lib/supabase/` | `packages/shared/src/supabase/`로 이동; 테스트와 서버 전용 보호 유지 |
| 루트 `package.json` | `private: true`, `apps/*`·`packages/*` workspaces, 앱별 실행 명령·통합 검사 명령 |
| 루트 의존성과 lockfile | Next.js·React는 앱에서, Supabase 의존성은 shared에서 명시; 기존 버전 유지, 루트 lockfile 재생성 |
| `next.config.ts`·`tsconfig.json` | 앱별 설정으로 이동·생성; `@/*`는 각 앱의 `src/*`만 가리킴 |
| `eslint.config.mjs` | 앱·패키지 코드 검사, 중첩된 `.next`·생성 타입·검사 산출물 제외 |
| `vitest.config.mts` | 루트가 앱·shared 설정을 수집; 기존 유닛 테스트를 새 위치에서 실행, 앱별 alias 분리 |
| `playwright.config.ts`·`tests/e2e/` | 두 앱의 빌드·전용 서버 설정; 기존 기본 화면 테스트 이동·조정 |
| `.env.example`·`.gitignore` | 앱별 환경변수 예시, 중첩된 빌드 산출물·환경 파일 제외 규칙 점검 |
| README·AGENTS·docs | 실제 모노레포 구조, 앱별 실행법과 책임으로 갱신 |

기존 클라이언트·검증·테스트의 동작을 보존한다. 구조 이동과 함께 로그인, DB 테이블, 에이전트 기능을 섞어 구현하지 않는다.

생성할 루트 명령은 `dev:onboarding`, `dev:interviews`, `build`, `lint`, `typecheck`, `test`, `test:e2e`다. 개발 서버는 두 터미널에서 각각 실행한다. npm의 전체 workspace 명령은 순차 실행되므로 장시간 실행되는 두 dev 서버를 동시에 띄우는 용도로 사용하지 않는다.

## 2단계: 최소 데이터와 온보딩

가상 구직자 1명의 이력서·근거 자료와 샘플 공고 3개를 준비한다. 우선 프로필은 구조화한 데이터로 저장하고 그래프 DB는 추가하지 않는다. 최소 필드는 경력, 역량, 근거 출처, 희망 직무·관심사, 연봉·근무 조건, 양보 가능한 조건, 추가 확인 질문이다.

Claude와의 인터뷰 후 사용자가 프로필을 확인·수정하고 확정한다. 이후 면접 앱이 같은 확정 프로필을 읽는다. 입력 검증, 모델 출력 검증, 오류와 재시도 표시를 포함한다. 공유 DB는 실행별 데이터와 접근 범위를 먼저 정하고 RLS를 포함해 구성한다.

실제 개인 자료 업로드와 OAuth 연동은 아직 만들지 않는다. 데모 UI에서도 가상 자료임을 명시한다.

## 3단계: 실제 에이전트 면접

하나의 확정 프로필과 샘플 공고를 바탕으로 구직자·채용 에이전트의 역할과 입력을 분리한다. 각 발언과 결과는 제공된 근거를 참조한다. 프로필에 없는 경험이나 수락 의사는 답변으로 만들어내지 않는다.

진행 상태와 최종 결과를 분리한다. 진행 상태는 대기·실행 중·사용자 확인 대기·완료·오류로 관리하고, 경험 조회·연봉 협의는 진행 중인 세부 단계로 표시한다. 완료 결과는 면접 추천·보류·조건 불일치로 구분한다.

API 실패·취소·제한 초과는 완료나 부적합 결과로 위장하지 않는다. 실행 시작 중복 방지, 호출 횟수·토큰·동시 실행 제한, 공개 API의 요청 제한을 포함한다. 실제 실행한 공고 수만 화면에 표시한다.

## 4단계: 검증과 배포 준비

구조 전환 후 두 앱의 lint·타입 검사·프로덕션 빌드와 기존 유닛 테스트가 통과해야 한다. 기본 화면 E2E는 두 앱을 검증하도록 조정하며, 기능 구현 후 온보딩 확정 → 면접 앱 이동 → 동일 프로필 조회를 검증한다.

Claude는 일상적인 자동 테스트에서 고정 응답으로 대체해 비용·변동성을 줄인다. 실제 API 대화는 별도 수동 스모크 테스트로 확인하고, 결과가 모델의 판단에 따라 달라질 수 있음을 고려한다. 데이터 계약·조건 확인·오류 상태를 중심으로 테스트를 추가하며, 전체 테스트 예산은 프로젝트 개요를 따른다.

Vercel에서는 같은 Git 저장소에 두 프로젝트를 연결하고 Root Directory를 각각 `apps/onboarding`, `apps/interviews`로 지정하는 안이다. 배포 시 공유 패키지 접근과 루트 lockfile 인식을 확인한다. 각 앱이 자기 `.next`를 사용하도록 하며, 같은 앱의 build·dev·E2E는 동시에 실행하지 않는다.

Supabase 공개 환경변수는 필요한 두 앱에, Claude API 키는 실제 Claude를 호출하는 두 앱의 서버 환경에만 설정한다. 앱 간 이동 URL도 배포 환경별로 설정한다. 실제 Vercel·Supabase 리소스 연결과 배포는 구조 전환 검증 후 별도로 진행한다.

## 실행 전에 확정할 남은 범위

우선 1단계의 구조 전환만 수행할지, 2·3단계의 제품 MVP까지 이어서 수행할지 확인한다. 샘플 공고 3개와 캘린더·외부 수집 제외는 제안이며 아직 확정 범위로 간주하지 않는다. Claude 모델과 실행 한도는 비용·대기 시간을 확인한 뒤 면접 엔진 구현 전에 정한다.

## 기술 근거

- [npm workspaces](https://docs.npmjs.com/cli/v11/using-npm/workspaces/): 기존 npm으로 앱과 공유 패키지 관리.
- [Vercel 모노레포](https://vercel.com/docs/monorepos): 앱별 Root Directory와 독립 프로젝트 구성.
- [Next.js workspace 패키지 처리](https://nextjs.org/docs/app/api-reference/config/next-config-js/transpilePackages): 공유 소스 처리 확인; 현재 자동 처리 범위를 먼저 확인하고 불필요한 설정을 추가하지 않음.
